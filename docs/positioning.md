# 定位、同类选择与路线图

[文档首页](README.md)

## 为谁解决什么问题

第一阶段服务已经使用 Codex 或 Claude Code 的个人开发者：代码任务做过了，但执行结果、证据、修订和日报分散在不同会话中，需要重新拼凑才能交接。

Work Assistant 围绕一条流程组织能力：**明确任务 → 复用本机编码 CLI → 留下来源和执行记录 → 更正结论 → 生成不可变报告 → 按授权交付**。飞书是交付适配器，Paseo 是可选的会话/调度宿主；两者都不该成为第一次看见报告的门槛。

最小可用体验是“只读检查自己的一个项目，并得到可追溯报告”。已有采集器也可提供验证过的 HTML/evidence bundle，不必迁移所有工作流。

## 怎样选择同类项目

以下是 2026-10-30 对各项目官方 README 的范围对照，不是性能、安全性或质量排名。上游会变化；某项未在本表出现，不表示对方没有实现。

| 项目 | 官方定位与入口 | 当你的主要需求是…… |
| --- | --- | --- |
| [OpenHands](https://github.com/OpenHands/OpenHands) | Agent Canvas 开发控制中心，组织多个编码 Agent、工作区及自动化 | 工程任务执行与更完整的 Agent 工作台，先评估它的工作区和集成能力 |
| [OpenClaw](https://github.com/openclaw/openclaw) | 跨设备、聊天渠道的个人助理，通过 Gateway 与 onboarding 接入 | 多渠道、日常个人助理和持续在线入口，先评估它的渠道生态 |
| [nanobot](https://github.com/HKUDS/nanobot) | Python 个人 Agent 框架，提供 CLI/WebUI、工具、记忆和聊天接入 | 轻量框架、自定义工具与自动化，先评估它的扩展方式 |
| [Hermes Agent](https://github.com/NousResearch/hermes-agent) | 持续学习的个人 Agent，提供安装、setup 和 doctor 路径 | 长期个人 Agent 与积累技能的工作流，先评估它的使用方式 |
| Work Assistant | 一次性 CLI、本地任务/证据/更正、离线报告、显式飞书投递 | 已有编码 CLI，希望补齐工作记录、交接和日报，且接受当前 Alpha 边界 |

复用编码 Agent、轻量运行、飞书接入、处理不确定结果，都不能单独宣称是本项目独创。我们没有跨项目同条件基准，不使用“更快”“更安全”“成本更低”等结论，也不以 star 数证明适用性。

## 竞争力如何验证

重点是把一个具体流程做好，而不是增加功能列表。以下标准对应公共产物和可重复的检查：

| 使用者应得到什么 | 检查方式 | 当前边界 |
| --- | --- | --- |
| 无账号也能看到完整结果 | README 的 demo；HTML、Markdown、证据与卡片预览齐全 | 合成输入，不证明真实模型质量 |
| 安装后离开源码目录仍能运行 | wheel 和 sdist 分别在干净 venv 安装、仓库外运行 demo | 构建工具可能联网；原生 Windows 不支持 |
| 知道自己缺哪个依赖 | 无 provider、Codex-only、Claude-only、DSH+Claude 的 doctor fixture | 不检测登录；Claude-only 路由仍有限制 |
| 知道结论来自哪里、为何改过 | demo 中 12→10 的更正、来源引用和旧报告不可变测试 | 不自动验证科学真实性 |
| 网络结果不明时不重复投递 | 注入超时/错误，检查持久 intent、GET 核对及 POST 计数 | 同一 journal 内的契约，不宣称跨平台 exactly-once |
| 别人能参与维护 | 贡献指南、issue/PR 模板、分发检查、平台 CI | Alpha 无长期支持承诺 |

这些是本仓库的验收标准，不是对其他项目缺少相应能力的判断。

## 下一阶段按什么顺序做

下面是待办方向和退出标准，不是已交付承诺，也没有虚构发布日期。

1. **验证外部用户真的能完成第一轮。** 收集至少三个独立安装环境的自愿反馈，记录从 demo、doctor 到首个只读任务/日报的卡点；不要求上传私人记录。只有外部复现支持后，才讨论稳定版。
2. **减少 provider 接入的特殊知识。** 为新 CLI 版本积累脱敏协议 fixture；评估 Claude-only 的显式路由方案。任何变更都必须保持授权检查，不能为了“开箱即用”绕过隔离或未知状态。
3. **让现有报告流程更容易接入。** 围绕公开 bundle 契约补充不同采集器的合成示例，要求保留来源限定、更正和哈希；不能只在维护者私有脚本中跑通。
4. **用公开案例证明持续使用价值。** 做一个从任务、发现、更正到交接的纯合成跨日案例；验收同时包括报告可读性、历史不变和投递不重复。再根据真实需求决定是否需要本地 UI。

暂不扩展团队 SaaS、通用渠道平台、第二套调度器或无边界自动执行。功能请求请描述要完成的工作、当前停在哪一步，以及可以怎样验证改进。
