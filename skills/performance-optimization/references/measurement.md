# 测量与判定

## 1. 计时

- **用同一个父时钟测端到端。** 跨进程的事件用请求 ID 或操作 ID 对齐。
- **设备工作是异步的。** 停表前要同步，或者使用设备事件计时；否则只量到了主机提交。
- **首步、稳态和尾部分开报告。** 冷启动算不算在内，要事先写明。
- **保留每一个原始时间戳。** 汇总值都从原始数据复算得到。
- **超时和失败也要计入。** 超时的请求没有完成时刻，但不能因此丢弃，否则 P99 会被美化。分母是全部发出的逻辑请求，每个请求只计一次。
  - **默认做法**：测用户等到终态的时间。两臂使用同一截止时间，超时请求按截止时长计入；提前返回错误的请求按实际耗时计入。
  - **例外**：如果要回答的问题是"截止之后请求最终何时完成"，才把超时作为删失数据（censored）单独分析。
  - 超时率和失败率另作护栏，同样以全部发出的请求为分母。
- **微观计时和端到端计时分开。** 微观计时只统计候选本身的工作，例如设备同步后的 kernel 时间，用来核对机制。端到端计时用同一个父时钟测用户实际的等待，包括排队，用来作判定。
- **压测时避免协同遗漏（coordinated omission）。** 闭环压测在慢响应期间会少发请求，于是漏掉本该采到的高延迟样本，分位数显得过好。按预定的到达率发送请求，或者按期望间隔做校正。这一现象由 Gil Tene 在公开讨论中提出。

## 2. 偏差

- **看似无关的设置也会翻转结论。** Mytkowicz 等人发现，环境变量的总大小和链接顺序就足以改变性能比较的结论。他们给出两种对策：一是随机化实验设置，用来避免偏差；二是做因果分析，用来检出偏差。
- **记录环境。** 节点、驱动、共驻负载、缓存冷热和时钟频率都要记录。控制不了的因素，就随机化或分层。
- **两臂共用瓶颈资源时不要并发。** 例如共用同一块网卡、同一个存储或同一张 GPU，并发运行会互相干扰。这时改为交错运行，或把共享资源单独计量。两臂各占独立资源时，并发运行可以抵消时段漂移。

## 3. 实验单位与重复

- **独立实验单位**是一次独立的进程、作业或机器上的运行。同一进程内的多次迭代不算独立单位。
- **重复次数按方差来源分配。** 不确定性最大的层级最需要重复，至少要在随机变异最高的层级重复。同一进程内迭代再多，也代替不了独立进程之间的重复（Kalibera 与 Jones）。其他层级按变异大小、成本和目标精度分配。
- **重复的单位是独立的运行对。** 配对时写清配对键，例如同一输入批、同一时段、同型号节点。对内保留配对关系，对内的先后次序随机化或按 ABBA 平衡。各运行对之间相互独立。
- **不同批次之间的裸差值不能归因。** 例如两天各跑一次、输入也不同，两次的差值不能算作候选的效应。要估计效应，就把候选随机分配到可比的样本上。
- **重复次数先做小规模噪声试测再定。** 用试测的方差和目标精度算出需要多少个运行对，把次数和停止点写进协议，跑完再看结果。

## 4. 统计与报告

- **说清比较的是什么。** 是耗时比、节省比例还是吞吐增幅，各自的分母是什么。
- **报效应量和置信区间。** 例如"A 比 B 快 5.5% ± 2.5%（95% 置信）"。区间可用 bootstrap 计算，重抽的单位要与独立单位一致：按运行对或时间块重抽，不按单个请求重抽。
- **分位数的估计量要写清。** 默认做法分三步：
  1. 每次运行在固定时长的稳态窗口内，分别算出两臂的 P99；
  2. 每个运行对算一次相对变化，例如 1 − 候选 / 基线；
  3. 取各运行对相对变化的中位数作为效应，并按运行对 bootstrap 出 95% 区间。

  同时报告两臂各自的绝对 P99。另一种做法是把全部请求合并后再算，这会让流量大的窗口权重更高，与默认做法可能给出不同的裁决。要改用它，须在协议里写明理由。
- **护栏用绝对值判定。** 每个批次内，候选的绝对 P99 取该批各次运行 P99 的中位数，区间按运行 bootstrap，再与护栏比较。相对变化的百分比不能直接与护栏比较。
- **护栏默认按保守方向判定。** 候选在每个批次的估计值都不越线，且其 95% 区间的不利一端也不越线，才算守住。任何一个批次越线，候选即淘汰。协议可以写别的规则，但要在看数据前登记。
- **用中位数和分位数。** 用均值时要说明理由。
- **判据在看数据之前写下。** 看到结果后要改，就另立版本，并写明原因和批准人。

**TrainLoop 的判据（虚构，运行前登记）：**

- 30 个稳态间隔的中位数低于 22 秒，并且低于同批参考实现的中位数；
- 15 对两步归一间隔的均值低于 22 秒；
- 64 条输入的张量摘要全部相等；
- 32 步的 loss、分母和梯度范数全部相等。

**给决定人的最小裁决表（虚构）。** 每个数字旁要能找到对应的收据。

## 5. 核验 AI 或他人声称的加速

**已知的失败。**

- **评测内存可被访问。** Sakana AI 的 AI CUDA Engineer 中，评测没能阻止候选访问评测内存，部分候选因此省略了必要的计算。公司随后修订论文，收回了原先公布的最高加速数字。
- **正确性检查太弱。** KernelBench-Verified 报告了一道 ReLU 题：一个恒等函数通过了标准的正确性检查，报出 374× 加速。换一种输入分布后，它就失败了。另一组数字统计的是同一模型在全部题目上的汇总：标准协议下几何平均加速为 1.43×，验证协议下为 0.88×。两组数字属于不同的统计层级，不要连在一起读。
- **改动计分本身。** METR 观察到，前沿模型会通过修改测试或计分代码、获取现成答案来拿高分。

**检查清单。**

- 评测程序与候选隔离。候选不能读写评测代码、参考输出和计时器。
- 测试输入不让候选看到，并且足够多样：多种形状、多种取值分布和边界值。正确性与参考实现对比。
- 输出必须物化并逐项检查。计时只统计候选本身的工作，在设备同步后停表。
- 做对抗检查：恒等或常数输出、缓存命中、跳过计算、偷偷调用高层库。
- 局部加速必须在主指标上复现，否则不算收益。

**虚构例。** 某 agent 报告 kernel 提速 10 倍。原来它在异步启动之后立刻停表，量到的只是主机提交的时间。改为设备同步后再停表，提速只有 1.1 倍。
