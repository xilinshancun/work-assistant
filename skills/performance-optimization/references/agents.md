# 多 agent 分工与契约

## 1. 角色

| 角色 | 负责 | 不做 | 交出 |
| --- | --- | --- | --- |
| 决定人 | 定指标、负载、护栏和预算；审候选卡；依协议放行、否决或升级给用户 | 不改评测程序；不在看到结果后改判据 | 预登记协议；判定记录，引用收据 |
| 提出者 / 实现者 | 写候选卡；改代码和测试；完成便宜层验证 | 不判定自己的收益；不改冻结项 | 候选卡、补丁或提交、单元测试和故障回放结果 |
| 独立评测者 | 在看到候选前冻结测试和计时程序；复算原始数据；做对抗检查 | 不按候选的意图调整判据；不改候选 | 评测收据：输入、版本、原始观测、复算结果、通过或否决的理由 |
| 运行者 | 申请资源、启动作业、收集原始观测、按时归还资源 | 不改协议；不申请超出授权的资源 | 运行收据：作业 ID、起止时间、原始数据路径和 SHA-256、资源归还证明 |
| 看门狗 | 定时检查进度、额度和时限；按书面接管规则接手 | 规则以外不自行决策 | 心跳记录、接管记录 |

**评测者需要知道什么。** 评测者要知道被测行为、输入、护栏和登记的硬判据，但不需要知道候选"希望"得到多大收益。

**"在看到候选之前冻结"的含义。** 评测者可以知道候选的想法。冻结要在读到补丁或实现之前完成，冻结的内容是测试输入、留出样本、计时程序和统计方法。已经知道的预期收益要记录下来。需要盲评时，由决定人另写一份不含预期收益的简报。

**四个签字点。** 这四步不要混为一谈。前两步都由评测者负责，但要分两次给出，而且不能由提出者签。
1. **上真实负载的资格**：评测者确认便宜层通过后给出。
2. **技术判定**：评测者依协议复算后给出。
3. **采纳**：决定人签署。
4. **对外发布或产生费用的授权**：用户批准。

**只有一个 agent 时。** 提出和决定由同一个 agent 兼任时，有三条规则：
- 另开一个新会话做评测和复算，由它签前两步。
- 这个 agent 可以签第三步"采纳"，但必须引用新会话的技术判定。技术判定未通过，就不能采纳。
- 第四步仍由用户批准。

无论如何，评测程序要在读到候选实现之前冻结。

**最终批准人。** 用户是外部动作、费用和产品取舍的最终批准人，见 [SKILL.md](../SKILL.md) §3。

## 2. 简报

子 agent 没有任何上下文，简报必须自足。Anthropic 在构建多 agent 研究系统时发现，含糊的一句话任务会导致子 agent 重复工作。每个子任务都应写明目标、输出格式、可用工具与来源，以及清楚的边界。他们还按任务规模给预算，避免在小事上过度投入。

```text
任务：<一句话，祈使句>
背景：<为什么做；相关决定>
相关文件：<路径> — <是什么、为什么重要>
交付：<文件路径与字段>；完成后回复 <内容>
可用：<工具、数据、来源>
边界：<不许做的事；不许改的文件；资源上限>
停止条件：<完成、失败或超时时怎么处理>
预算：<时间、token、GPU>
```

## 3. 契约与收据

- **预登记。** 运行前登记指标、负载、判据、预言、冻结项和版本号。评审接受后冻结。
- **改动。** 改判据或冻结项时另立版本，写明原因和批准人。
- **收据字段：**
  - 路径；
  - SHA-256；
  - 产生时间和产生者；
  - 输入版本；
  - 产生它的命令。
- **进度与交接。** 进度日志和 git 历史让新会话能从磁盘接手。这与 Anthropic 为长时运行 agent 设计的做法一致。交接文件写明四项：
  - 当前状态；
  - 已否决的方案；
  - 下一步；
  - 不可越过的条件。
- **资源。** 谁申请，谁归还。运行失败也要归还资源，并留下证明。

## 4. 编排方式

| 情形 | 方式 |
| --- | --- |
| 子任务可分且依赖少，例如多个候选的便宜层验证、多来源调研 | 编排者分派，多个 worker 并行 |
| 判据清楚，迭代有可测的收益，例如 kernel 参数或配置搜索 | 生成者与评测者循环 |
| 卡住、需要否证或方案有分歧 | 请第二意见，或组织委员会 |
| 共享上下文多、步骤强依赖，例如一次真实负载运行 | 串行，由一个运行者负责 |

多 agent 的代价很高：Anthropic 报告，其多 agent 系统消耗的 token 约为普通对话的 15 倍。只在收益值得时使用。Anthropic 也指出，各 agent 必须共享大量上下文、或彼此依赖很多的任务，目前不适合拆分。

**AI 擅长什么。** AI 擅长生成大量候选和迁移已知模式，不擅长定位瓶颈。在 GSO 基准上，领先的 agent 成功率低于 5%，作者分析的轨迹显示它们难以准确定位瓶颈。所以瓶颈靠时间线定位，结论由独立评测判定。

**工业实例（均为公司自报）：**

- **Meta。** FBDetect 在生产环境检测细小回归，AI Regression Solver 为回归生成向前修复的 PR，由引入回归的变更作者评审。Meta 的容量效率平台用同一套工具接口做"防守"和"进攻"。"防守"是检测回归并修复，"进攻"是发现优化机会并提交 PR。两者只有 skill 层不同，而 skill 层承载的是资深效率工程师的经验。
- **Google ECO。** 它分五步工作：从历史提交中挖掘性能反模式；用全机群的持续 profiling 定位性能关键代码；由模型改写；经自动测试、模型自审和代码评审；最后上线并监测效果。作者报告已落地 6,400 多个提交。

## 5. TrainLoop 的分工（虚构）

1. **决定人登记协议。** 内容包括主指标、64 条输入、判据、护栏和预言。独立评测者审阅后冻结。
2. **实现者提交候选。** 候选为"客户端保持三步在途"，附候选卡、单元测试和故障回放。
3. **独立评测者先审候选。** 评测者确认故障路径没有新增阻塞，给出上真实负载的资格。
4. **运行者执行同批两臂。** 运行者申请资源，两臂在同批输入上并发运行，然后交回原始时间戳、数值摘要和资源归还证明。
5. **评测者复算并给出技术判定。** 评测者从原始数据复算主指标，判定满足硬判据。
6. **决定人安排复现，然后签署采纳。** 新样本上的复现通过后，决定人签署采纳。改默认配置属于产品取舍，交用户批准。

另一个候选"提前发出采集请求"在第 3 步的故障回放中被否决，记入反例库。

运行期间，看门狗每 30 分钟检查进度和额度。决定人会话的额度用尽时，看门狗按书面规则接手，完成资源归还和记录。
